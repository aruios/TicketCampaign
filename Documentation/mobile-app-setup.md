# iOS App Setup (local)

`../FlightCampign/FlightCampign.xcodeproj` is wired up to Supabase and
Stripe: the target was converted from the macOS template Xcode generated by
default to a real iOS app, the `supabase-swift` and `stripe-ios` Swift
Packages are already declared as dependencies (added by hand-editing
`project.pbxproj`, since the `xcodeproj` gem doesn't yet understand this
project's file format and there's no `xcodebuild` subcommand for adding a
package), and the screens described below already exist under
`FlightCampign/FlightCampign/Features/`. What's left is genuinely local:
running it against your own Supabase instance.

## Prerequisites

- Xcode with an iOS 18+ simulator (Sign in with Apple and modern SwiftUI
  features assume a recent OS; the project targets iOS 26.0 to match this
  machine's Xcode/SDK version — lower `IPHONEOS_DEPLOYMENT_TARGET` in
  `project.pbxproj` if you need to support older devices)
- Local Supabase running (`backend-setup.md`), including the
  `create-pledge-intent` Edge Function (see §5 below)
- A physical device is needed later for push notifications — APNs doesn't
  deliver to the simulator (local notifications still work for testing UI)

## 1. Open the project

```bash
cd ~/Documents/Flight_Ticket_Scope/FlightCampign
open FlightCampign.xcodeproj
```

Xcode will resolve the Swift Package dependencies (`supabase-swift`,
`stripe-ios`) automatically on first open — this can take a while since
`stripe-ios`'s repository is large (~3GB before Xcode prunes it down to the
checked-out revision).

## 2. Swift Package dependencies (already declared)

| Package | URL | Product used |
|---|---|---|
| supabase-swift | `https://github.com/supabase/supabase-swift` | `Supabase` (Postgres queries, Auth, Storage, Edge Functions) |
| Stripe iOS SDK | `https://github.com/stripe/stripe-ios` | `StripePaymentSheet` |

## 3. Local config (already wired, no xcconfig needed)

Simulators can reach your Mac's `localhost` directly, so
`http://127.0.0.1:54321` works from the simulator without any tunnel. (A
physical device on the same Wi-Fi needs your Mac's LAN IP instead, e.g.
`http://192.168.1.23:54321` — find it with `ipconfig getifaddr en0`, and
update the build setting below to match.)

Rather than a separate `Config.xcconfig`, the three values are set directly
as `INFOPLIST_KEY_*` build settings on the app target in `project.pbxproj`
(Xcode's auto-generated Info.plist passes any `INFOPLIST_KEY_<Name>` setting
straight through as top-level key `<Name>`):

```
INFOPLIST_KEY_SUPABASE_URL = "http://127.0.0.1:54321";
INFOPLIST_KEY_SUPABASE_ANON_KEY = "placeholder-anon-key";
INFOPLIST_KEY_STRIPE_PUBLISHABLE_KEY = "pk_test_placeholder";
```

Replace the placeholders with the real anon key from `supabase start` and
your Stripe test publishable key once you run `backend-setup.md` for real —
edit both the Debug and Release configurations. `FlightCampign/Config.swift`
reads them via `Bundle.main.object(forInfoDictionaryKey:)`. Never put the
`service_role` key here — the anon key plus RLS (`backend-setup.md` §4) is
what's supposed to protect data on-device.

## 4. Supabase client and Stripe (already wired)

`FlightCampign/Services/SupabaseService.swift` creates the shared client:

```swift
let supabase = SupabaseClient(
    supabaseURL: Config.supabaseURL,
    supabaseKey: Config.supabaseAnonKey
)
```

`FlightCampign/FlightCampignApp.swift` sets the Stripe publishable key at
launch. `Services/SessionStore.swift` observes `supabase.auth.authStateChanges`
and is what `ContentView` uses to decide Onboarding vs. the tab bar.

Pledging uses a Stripe **PaymentIntent with `setup_future_usage:
"off_session"`**, not a card hold or a bare SetupIntent — this charges the
refundable deposit immediately *and* saves the card for the off-session
balance charge later, in one `PaymentSheet` confirmation. The product doc's
warning about card holds still applies: Stripe holds expire around 7 days,
and pledge windows run longer, which is why this isn't a hold.

The client secret is never created on-device — `Features/Pledge/PledgeView.swift`
calls the `create-pledge-intent` Supabase Edge Function
(`kootam-backend/supabase/functions/create-pledge-intent/index.ts`), which
holds the Stripe secret key server-side, creates/reuses a Stripe Customer for
the signed-in user, and returns a client secret + ephemeral key for
`PaymentSheet`. Deploy it before testing a real pledge:

```bash
cd kootam-backend
supabase functions deploy create-pledge-intent
supabase secrets set STRIPE_SECRET_KEY=sk_test_...
```

## 5. Capabilities still needing Xcode's GUI

These need your Apple Developer account signed into Xcode and can't be set
safely by hand-editing `project.pbxproj` (a wrong entitlement here breaks
code signing) — add them from the **Signing & Capabilities** tab:

- **Sign in with Apple** — the Onboarding screen already has the button
  (`SignInWithAppleButton` in `Features/Onboarding/OnboardingView.swift`),
  but tapping it will fail until this capability is added (it generates the
  `com.apple.developer.applesignin` entitlement).
- **Push Notifications** — funded/ticketed/deadline-reminder alerts
- **Background Modes → Remote notifications** — so status pushes can update
  "My Trips" without opening the app
- **Associated Domains** (`applinks:`) — for the universal link used by
  `ShareLink` in `CampaignDetailView` (currently pointed at a placeholder
  `kootam.app` domain — update once you have a real one)

None of these are testable in the simulator except UI layout — push and
universal links need a real device and, for push, an APNs key uploaded to
Supabase.

## 7. Run it

Select an iOS simulator, `Cmd+R` (or `xcodebuild -scheme FlightCampign
-destination 'generic/platform=iOS Simulator' build` from the CLI — this is
what was used to verify the target builds after conversion). With placeholder
config values the app builds and Onboarding renders, but network calls will
fail until `backend-setup.md`'s `supabase start` is actually running and the
real anon key is in the `INFOPLIST_KEY_*` settings above.
